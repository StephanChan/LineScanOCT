cellpose_organoid_segmentation.py — 3D organoid segmentation

Segment organoids in an OCT volume or stitched mosaic (stitched-*.tif, processed page-by-page when it is too large for RAM) with Cellpose. Runs by pressing Run/F5 in Spyder - no command window needed - and writes the labels back in the input orientation together with per-organoid statistics and a QC figure.

1  Overview

The script is standalone (no Qt, no hardware imports) and runs from Spyder (first row / F5) or from the command line via run_cellpose_organoid_segmentation.bat. It is deliberately written in the same style as the other data_processing scripts: DEFAULT_* settings at the top, an argparse interface, main(), and import tifffile as TIFF.

What happens for each input volume:

  1. read the TIFF as [Y, X, Z] (one page per Y row),
  2. optional Y/X crop and depth range (crop, depth_range),
  3. estimate the working set and decide single pass vs Y strips for stitched mosaics,
  4. OCT display compression (20*log10 + dynamic-range clip) plus a percentile stretch,
  5. optional de-speckle smoothing and integer downsampling,
  6. transpose to Cellpose's [Z, Y, X] layout and run Cellpose (3d / 2d-stitch / projection),
  7. transpose the labels back to [Y, X, Z], paste them into a full-size label volume, filter small fragments, and write the mask TIFF, statistics CSV, QC PNG and JSON summary.

Sections 4-7 cover the Spyder workflow, the modes, how the 3D segmentation works, and how mosaics are processed. Sections 8-12 are reference.

Why a dedicated script instead of Cellpose's own CLI? Two OCT specifics. (a) The saved layout is [Y, X, Z], one TIFF page per Y row - Cellpose 3D wants [Z, Y, X], so an axis swap is mandatory in both directions. (b) Raw OCT amplitude spans several orders of magnitude (noise floor ≈ 1e-5, tissue ≈ 10-100, brightest surface voxel ≈ 500 in the organoid tiles), so Cellpose's built-in 1-99 percentile normalisation alone is not enough; the dB compression below is what makes the organoid boundaries visible to the network.

Windows DLL conflict: OSError: [WinError 127] ... torch\lib\shm.dll

If import torch fails like this, Cellpose and torch are installed correctly - Windows is loading the wrong build of a dependency. A pip-installed torch ships its own Intel OpenMP, MKL and CUDA DLLs in site-packages\torch\lib; a conda-forge environment ships different builds of the same file names in <env>\Library\bin:

<env>\site-packages\torch\lib\libiomp5md.dll    1.5 MB   (torch's own)
<env>\Library\bin\libiomp5md.dll                0.2 MB   (conda-forge)
<env>\Library\bin\mkl_rt.2.dll and friends

Windows resolves a dependency by file name and reuses whichever copy was loaded first, so if numpy/scipy/MKL load before torch - which is what happens under Spyder, where the console has usually imported them already - torch's DLLs bind to the conda-forge OpenMP build, which lacks symbols they need. WinError 127 means "the specified procedure could not be found"; a missing file would be WinError 126.

The script now fixes the order itself, before it imports numpy: it puts torch's own DLL directories (including nvidia/*/bin|lib) at the front of PATH, registers them with os.add_dll_directory, sets KMP_DUPLICATE_LIB_OK, and imports torch first. It reports what it did at the top of each run and in the summary JSON (torch_dll_bootstrap).

If it still fails, in order:

  1. Do nothing. If torch cannot be imported in the process the script is running in (typical for a Spyder kernel that has been alive for a while - it cannot be repaired from the inside, because a loaded DLL can never be unloaded), the script now re-runs the pipeline in a fresh interpreter, streams that output into the console, and returns the results as usual. You will see a banner with the child command line; no restart is needed. Disable with DEFAULT_USE_SUBPROCESS_FALLBACK = False or --no-subprocess-fallback.
  2. Restart the Spyder kernel (Consoles > Restart kernel) if you prefer everything in one process. Then the bootstrap wins on the first run - do not import numpy/matplotlib in that kernel beforehand.
  3. Use a dedicated environment so torch never sits next to a conda-forge OpenMP/MKL build: 
    conda create -n cellpose_env python=3.11 -y
conda activate cellpose_env
pip install "cellpose[gui]"
    then set CONDA_ENV in run_cellpose_organoid_segmentation.bat (or the Spyder interpreter) to C:\Users\shuaibin\.conda\envs\cellpose_env. This is the reliable long-term fix and also protects the acquisition environment from torch's pins.
  4. Inspect the order with torch_dll_report() (prints every conflicting DLL name with its directory and size, in search order) and torch_dll_directories() (the paths the bootstrap chose). For a temporary escape hatch, DLL_BOOTSTRAP_ENABLED = False disables the bootstrap entirely.

Related but distinct: OMP: Error #15 ("libiomp5md.dll already initialised") is the duplicate-runtime abort - in this environment caused by torch's Intel OpenMP (torch\lib\libiomp5md.dll, 1.5 MB) meeting conda-forge's LLVM OpenMP (llvm-openmp 22.1.0: Library\bin\ libomp.dll + a 0.15 MB libiomp5md.dll shim, plus libgomp-1.dll and vcomp140.dll). The KMP_DUPLICATE_LIB_OK=TRUE that the bootstrap sets suppresses it; the fresh-process path avoids it altogether. A CUDA build whose runtime is newer than the driver (560.76 = CUDA 12.6 here) can produce the same WinError 127 - in that case install a matching torch build or run with --no-gpu. A CPU-only wheel (torch 2.14.0+cpu) is reported once and Cellpose then runs on the CPU.

3  Data layout

  • A volume is [Y, X, Z]: one TIFF page per Y row, page shape [X, Z] (X camera lines by Z depths), float32 amplitude.
  • File names are tile-{n}-Y{y}-X{x}-Z{z}.tif (see FileNaming.py); the stitched mosaic is stitched-Y{y}-X{x}-Z{z}.tif and the dynamic/mean tiles are tile-{n}-{Mean|Dyn}-Y{y}-X{x}-Z{z}.tif. Any of them work.
  • Example used for validation: E:\IOCTData\BJRcellcluster\0922\sampleID-1\Time-2\tile-1-Y575-X1016-Z76.tif → [Y=575, X=1016, Z=76], 0.178 GB.
Reading multi-page files. Some of these TIFFs are stored so that tifffile reports one series per page (575 pages / 575 series on the tile above), and tifffile.memmap then returns only a single page. The script verifies that a memory map covers the whole file (size == pages × page_shape) and falls back to explicit page stacking when it does not, printing a note. If you write your own loader, do the same check - otherwise you silently analyse only the first Y row.

4  Running in Spyder

The script is built for Spyder: no command window or shell is needed. Open data_processing\cellpose_organoid_segmentation.py in Spyder, press Run (F5), and the DEFAULT_* block at the top of the file is used as-is. USE_COMMAND_LINE_ARGS is False, so any stray arguments (for example Spyder's -f) are ignored with a printed note instead of an argparse error.

Option A - edit the settings block and press F5

)

DEFAULT_DYNAMIC_RANGE_DB = 35.0    # OCT contrast - the parameter that matters most

DEFAULT_TILE_Y = 0                 # 0 = let the script decide (auto Y strips)
DEFAULT_DRY_RUN ...                # see below: add dry_run=True to segment_organoids()

Option B - call it from the Spyder console (no editing, no restart)

Works because %autoreload reruns the file, but the simplest way is to run the file once and then use the console:

The return value is a list of {"summary": ..., "records": ...} per volume, which you can keep exploring in the console:

Option C - the command line (optional)

Only if you want it: run_cellpose_organoid_segmentation.bat adds the environment's Library\bin to PATH (needed for the numpy/tifffile/torch DLLs on Windows) and passes --use-command-line-args, which switches argument parsing on for that run:

You can also set USE_COMMAND_LINE_ARGS = True in the file if you prefer arguments to win over the DEFAULT_* block.

Always start with dry_run=True (Spyder) or --dry-run (shell). It exercises reading, cropping, compression, statistics, writing and the QC figure with a crude threshold instead of Cellpose, so you can confirm the axes, the depth window and the output orientation in seconds without a GPU or a Cellpose install. Add crop=(y0, y1, x0, x1) to keep the first real Cellpose call small.

5  Modes (--mode)

ModeCellpose callWhen to use
3d (default) do_3D=True, z_axis=0, anisotropy=z/xy Full 3D segmentation: 2D flows are predicted on the XY, ZY and ZX planes of the volume and merged, so partial organoids are still one object. Needs --xy-pixel-um/--z-step-um to be right, and needs enough Z extent and signal. Most memory/VRAM hungry.
2d-stitch do_3D=False, stitch_threshold=0.5 Cellpose segments each Z plane and stitches the planes into 3D labels by IoU. More forgiving when Z is coarse, noisy, or when only a few planes contain the organoid. Often the most robust choice for strongly anisotropic OCT data.
projection 2D on the en-face projection Organoid counting and XY cross-section measurement. The mask output is a 2D [Y, X] label image named cellpose_maskXY_*.tif. Use --depth-range to restrict the projection to the focal band, and --projection max|mean to choose the projection.

Because the en-face plane carries the highest resolution in a line-scan OCT volume, projection is the cheapest useful sanity check, and 2d-stitch is usually the best compromise for true 3D labels.

6  How the 3D segmentation actually works

Cellpose is a 2D network, so "3D" mode is a way of making a volume out of 2D predictions. This is what happens to your mosaic, end to end.

6.1  From the file to Cellpose's grid

  1. Read - one TIFF page per Y row gives [Y, X, Z].
  2. Compress - raw amplitude → dB, clip to --dynamic-range-db, stretch to 0-1. Without this step the surface reflection and the speckle dominate and the network sees noise.
  3. Transpose to [Z, Y, X] (Cellpose's 3D layout) and optionally smooth and downsample.
  4. Anisotropy - Cellpose resamples Z so the volume becomes isotropic, using anisotropy = z_step / xy_step (its own convention is "2.0 if Z is sampled half as densely as X or Y"). On this system 4.4 um / 0.833 um ≈ 5.3, so Z is interpolated about 5x finer before the network sees it, and the labels are mapped back to the original grid afterwards.

6.2  What the network predicts

For every 2D plane the network emits, per pixel, a horizontal flow, a vertical flow and a cell probability (the probability is passed through a sigmoid centered at zero, so it ranges roughly −6…+6). Flows point "uphill" towards the centre of the object each pixel belongs to. Cellpose-SAM additionally runs the same network on all three orthogonal plane sets of the volume and adds the results:

run_3D:  YX planes  +  ZY planes  +  ZX planes  ->  (Z flow, Y flow, X flow, cellprob)

That is straight from cellpose's own core.run_3D ("running YX: 76 planes of size (2272, 2515)" etc.), and it is why 3D mode costs roughly three times a 2D pass over the same voxels.

6.3  From flows to organoid labels

Voxels whose cell probability exceeds --cellprob-threshold are then moved along the predicted flows for --niter iterations (default: scaled to the object size). Voxels that converge to the same point form one object and get one label - the objects are the basins of attraction of that flow field. Afterwards:

  • --flow-threshold (0.4): the flow gradients of each candidate object are recomputed and compared with the network's flows; objects whose mean squared error is above the threshold are discarded as malformed. Raise it if real organoids are missing, lower it if you get blobs of nonsense shapes.
  • --min-size (voxels): objects smaller than this are removed by Cellpose itself. This is the main speckle filter in 3D.
  • --diameter: Cellpose-SAM was trained on objects of 7.5-120 px (mean 30) and is largely scale invariant; passing a larger diameter makes the network downsample first, which is faster. 0 lets it decide.

6.4  What comes back, and what this script adds

  1. Cellpose returns masks as [Z, Y, X] (plus flows and, in Cellpose 4, a zero style vector).
  2. The script transposes the labels back to [Y, X, Z], pastes them into a full-size label volume (so the mask always matches the input TIFF, including any --crop/--depth-range), and drops objects below --min-volume-voxels.
  3. Every remaining object is measured: voxel count, physical volume, sphere- equivalent diameter, centroid and bounding box, one CSV row each.
Why 2D+stitch exists (section 5): that mode skips the flow merging, segments each Z plane independently and then links planes whose masks overlap enough (stitch_threshold, IoU). It is more robust when Z is coarse or the volume is noisy, and it is a good cross-check on the 3D result.

7.1  The memory decision

One Cellpose 3D call needs roughly 32 bytes per voxel (the loaded strip, its compressed copy, the four flow/cellprob planes, Cellpose's mask and our label volume). The script estimates that for the selected crop/depth window and compares it with --max-ram-gigabytes (default 24 GB of your 32 GB):

Tiling : auto: whole volume needs ~13.9 GB > 8.0 GB, so 512-row Y strips (~3.1 GB each) are used

Set --tile-y N to force a strip height; projection mode needs no tiling at all.

7.2  How strips avoid splitting organoids

  • Core - the tile_y rows a strip is responsible for; read range - core plus --tile-overlap-y rows on each side, so Cellpose still sees whole objects near a boundary. Only those pages are read from the TIFF.
  • Ownership by centroid - a strip writes only the objects whose centroid Y lies in its own core. The neighbouring strip drops its copy. Every organoid is therefore written exactly once and whole, with no merge pass and no double counting.
  • No clobbering - a strip only fills voxels that are still background, so an object tail already claimed by a neighbour is untouched.
  • Overlap must exceed the object size - an object longer than 2 x tile_overlap_y can still be split. The default is 64 rows and the script warns in the first strip if a measured object is longer than that.

The mask is written as a memory-mapped BigTIFF covering the full mosaic ([Y, X, Z], uint16) and is then re-measured in Y chunks, so the CSV and the mask agree exactly even where a seam handed a few voxels to a neighbouring object.

Every strip prints its own duration, split into reading + preprocessing, Cellpose and the label bookkeeping, together with the running mean and the estimated time left for the remaining strips; the JSON summary keeps them in strip_seconds and strip_seconds_mean.

Strip-mode limits. --save-seg-npy is skipped (the mask is already a memory-mapped BigTIFF), and an organoid longer than the overlap in Y can appear as two objects. For counting a whole mosaic the fastest and safest option is often --mode projection: it projects the mosaic page-by-page into a single 2D en-face image (no seams, tens of MB of RAM) and segments that, using the raw-amplitude projection so the strips need no global normalisation.

8  Preprocessing

Intensity compression (--compression)

Default db maps amplitude a to clip(20*log10(a) - max + R, 0, R)/R with R = --dynamic-range-db (35 dB). In other words: the brightest voxel becomes 0 dB, everything more than 35 dB below it is clipped to black, and the result is stretched to 0-1. --compression log is a plain log1p variant, none keeps the linear values. A percentile stretch (--percentile-low 1, --percentile-high 99.9) is then applied in all cases.

Tuning guide for --dynamic-range-db: larger (→ 45-50 dB) keeps more of the dim organoid interior and tends to merge neighbouring organoids; smaller (→ 25-30 dB) isolates only the bright organoid bodies. This single parameter usually changes the result more than any Cellpose threshold.

De-speckling (--smooth-xy, --smooth-z)

OCT speckle is multiplicative, high-frequency and coherent - exactly what Cellpose is not trained on. A Gaussian sigma of 0.5-1.5 px in XY (and optionally 0.5-1 px in Z, remembering that Z is ~5x coarser) removes most of it without blurring organoid boundaries away. Start with --smooth-xy 1.

GPU preprocessing (--preprocess-device)

Compression, percentile stretch, de-speckling and the projection are the CPU-bound half of a run: numpy/scipy touches every voxel, and once Cellpose itself runs on the GPU this is the only CPU work left (the GPU was measured at ~5 % with ~2 CPU cores busy). --preprocess-device auto - the default - therefore runs the same four steps in torch on the GPU whenever torch sees a CUDA device; cpu always uses numpy/scipy (bit-for-bit the previous behaviour) and gpu asks for the GPU and prints the reason when it has to fall back (no CUDA device, a CPU-only torch build, or the Windows DLL conflict in a long-lived Spyder kernel, where auto silently stays on the CPU). Every run prints which one it used and the summary JSON records preprocess_device / preprocess_device_reason.

The torch path is the same arithmetic, not an approximation: the Gaussian uses scipy's own kernel, radius and border mode, and the padding is replicate for scipy's nearest. On a real mosaic crop the two implementations agree to 1.3e-06 and give the same labels (verified with --dry-run: strip mode bit-identical in one pair of runs, 8 differing voxels of 11.7 M in the other; single-pass 8 of 11.7 M, both with the same object count). Only the percentile pair is estimated - from a uniform-stride subsample above 16 M voxels, because torch.quantile sorts - which shows up as ~3e-07 in the result. Use --preprocess-device cpu if you need the numpy numbers exactly.

Measured on a 300 x 600 x 65 crop: 0.53 s (numpy) → 0.09 s (torch). The gap grows with the volume, because the CPU cost is proportional to the voxel count while the GPU cost is not. It does not remove the RAM peak of a 3D run: Cellpose's flow field, sparse dynamics and tile stitching stay on the CPU and still scale with Z x Y x X (that is what the MemoryError is about) - use --depth-range, --tile-y or --downsample for that. The Z upsample Cellpose performs for anisotropy is inside Cellpose (OpenCV, on the CPU) and is not ours to move.

Preproc: device=gpu (torch 2.14.0+cu126, NVIDIA GeForce RTX 3060), db 35 dB, smooth xy=1 z=0.5 px

Check the backend, and how exact it is, from the console - in a fresh process, since torch cannot be imported inside a Spyder kernel (there the report correctly says cpu and prints the DLL reason):

Roundness (sphericity)

Every 3D object also gets surface_area_um2 and roundness, and the third QC panel is a roundness histogram. The area is the sum of the object's exposed voxel faces weighted by their real size (a Z-normal face is an X-Y plane = xy_um², the others xy_um * z_um), so anisotropic sampling is handled. Roundness is Wadell sphericity, pi^(1/3) * (6V)^(2/3) / A, with A divided by 1.5 first: counting voxel faces overestimates a smooth surface by exactly that factor (the mean of |nx|+|ny|+|nz| over a surface, i.e. the staircase area), so after the correction a digitised sphere reads 1.00. Measured calibration on synthetic shapes:

Shaperoundness
sphere1.00 (1.002 isotropic, 0.995 on the 1.666 x 4.4 um grid)
ellipsoid 2:1:10.95
rod 6:1:10.83
two touching lobes0.81
cube1.21 - flat-faced objects overshoot, the correction assumes a smooth surface

Caveats: --downsample makes the mask blocky and lowers roundness by a few percent, so use --downsample 1 when shape is the point; Z is coarse (4.4 um per plane), so objects only a few planes thick are dominated by discretisation and are best compared with objects of similar thickness; roundness is a ratio, so the objective / --xy-pixel-um question moves surface_area_um2 much more than it moves roundness; with both pixel sizes 0 the two columns fall back to voxel counts and face counts; --min-volume-voxels is applied first, so the histogram only covers objects that survived it. In strip mode the columns are measured on the written mask in Y chunks, so they match the mask exactly.

11  Tuning recipe

  1. Orientation first. In Spyder run segment_organoids(dry_run=True, depth_range=(z0, z1)) and open the QC PNG. The en-face panel must look like an XY organoid image (round blobs), not like a B-scan; the mask must sit exactly on the bright tissue. Only then continue.
  2. Depth window. Pick depth_range from the B-scan / X-Z view of the stack in your viewer so the surface reflection and the noise floor are excluded.
  3. Contrast. Try mode="projection" with smooth_xy=1 and scan dynamic_range_db over roughly 25 / 35 / 45; keep what makes the organoid bodies cleanest. Because the projection is a single 2D image this is also the fastest way to iterate.
  4. A first real 3D run on a crop. segment_organoids(crop=(0, 512, 0, 1016), depth_range=(5, 70), diameter=60) to see real organoid labels in about a minute, with tile_y=0 so there are no strips yet.
  5. Then the whole mosaic. Drop crop and let the tiling decide itself; if it picks strips, watch the printed per-strip "kept N object(s)" lines and the overlap warning. Use mode="2d-stitch" when the 3D result fragments.
  6. Counts. If organoids are missed lower cellprob_threshold to about -1; if speckle blobs pass, raise min_size, min_volume_voxels and cellprob_threshold.
  7. Correct by hand if needed. Add save_seg_npy=True (single-pass volumes only), load the *_seg.npy in the GUI (python -m cellpose), fix the ROIs, and export.

12  Notes & caveats

  • Cellpose models are trained on cells, not organoids. Cellpose-SAM zero-shot generalises well, but for a quantitative study fine-tune on a few hand-labelled volumes (cellpose[gui] training, then --model <path or name>).
  • Anisotropy. Z is much coarser than XY on this system (4.4 um vs 1.666 um at 10X, or 0.833 um at 20X, i.e. 2.6x-5x). --mode 3d up-samples Z internally to make the volume isotropic, which multiplies memory and time by that same factor; if that is too expensive, use --mode 2d-stitch or a smaller --crop/--depth-range.
  • Memory is handled for you. The script estimates one Cellpose pass at ~32 bytes/voxel and either runs the whole volume or switches to Y strips automatically; the strip mask is a memory-mapped BigTIFF, so a 2 or 5 GB mosaic never has to fit in RAM. Set --max-ram-gigabytes to the real headroom you have (the default 24 GB assumes most of your 32 GB is free, so lower it if the OCT app or Spyder is busy).
  • Strips need a large enough overlap. An organoid longer than 2 x tile_overlap_y in Y can be split into two labels near a strip boundary; the script warns when it sees one. Raise tile_overlap_y to at least the organoid diameter, and tile_y to 512-1024 so the extra context does not dominate the runtime. For pure counting, --mode projection avoids the question entirely.
  • Cellpose's sparse-invariant warning is silenced. Cellpose builds a torch.sparse_coo_tensor for its 3D neighbour graph and torch warns once per process that the sparse invariant checks are "implicitly disabled". The script calls torch.sparse.check_sparse_tensor_invariants.disable() right after the model is loaded, which states that explicitly - the fix the warning itself asks for. Behaviour is unchanged: the checks were already off, and enabling them would only add overhead and risk hard failures on a large mosaic.
  • Cellpose errors are not covered by the dry run. dry_run=True tests the plumbing; the first real run is what exercises the model. Start it on a crop of the mosaic to see the real quality in a minute, then scale up.
  • Spyder vs shell. USE_COMMAND_LINE_ARGS = False keeps Spyder happy (stray arguments are ignored with a note). If you ever want arguments to be authoritative, set it to True or pass --use-command-line-args (which the .bat launcher does).
  • Outputs live in their own folder. Everything goes into <input folder>/segmentation_results/ (a relative --output-dir is created under the input's folder; pass an absolute one or "" to change that). The folder is reused if it already exists and the file names come from the input stem, so re-running a volume replaces its mask, CSV, QC PNG and summary in place. In strip mode the mask BigTIFF is deleted and rewritten, so close it in any viewer first. Folder scans skip cellpose_* files, so the results folder is never picked up as input (even with --recursive).
  • Validate the labels. Always inspect the QC PNG and the largest-object X-Z section before trusting the counts, especially when touching --dynamic-range-db.
